# Week 2 Task 2.6 — Production Model Packaging Report

## Selection summary

The frozen Task 2.4 Random Forest is packaged without retraining. LightGBM-log was the best advanced validation-RMSE model and CatBoost-log the best advanced test-RMSE model, but neither was selected from test performance alone. Random Forest retained the best validation MAE (365.49), best overall test RMSE (59,372.42), stable deterministic behavior, and a complete sklearn preprocessing pipeline. LightGBM’s validation-RMSE advantage was only 0.41% and came with worse validation MAE and test RMSE.

## Artifact audit

Source: `models/baseline/random_forest.joblib`, SHA-256 `67f244e576cb2b2b161a04f72499e5b00d2ac2361669561472edee5a14bff507`.

The artifact contains:

- 42 expected engineered predictors in a fixed named order

- A fitted 30-tree Random Forest with seed 42

Clean-process loading, finite prediction, deterministic repetition, column reordering, missing columns, extra columns, unsupported categories, and source/package parity were tested.

## Versioned package

`models/production/current.json` activates `models/production/v1.0.0/`. The directory contains the copied model, schema, metadata, metrics, requirements, model card, examples, README, and SHA-256 manifest. The source and packaged model hashes are identical. The packaging script builds in a temporary directory, verifies checksums and inference, renames only a complete package, and writes the active manifest last. Existing versions are never overwritten by default.

## Production input and feature parity

The contract requires 15 raw application fields: building and site IDs, meter, timestamp, primary use, building attributes, and weather measurements. `building_id` and `site_id` are required for traceability and warnings even though they are excluded from model predictors. `meter_reading` is prohibited.

`ml_service/inference.py` calls `create_features_for_inference` from `scripts/week2_feature_engineering.py`; calendar, cyclical, building, weather, and interaction formulas therefore share one implementation with Task 2.3. The resulting frame is explicitly aligned to the 42 fitted predictor names. No training dataset is loaded during inference.

## Validation and errors

Missing or extra fields, target leakage, non-finite values, unsupported meter codes, impossible timestamps, negative area, invalid vintage/floors, and invalid wind direction raise a safe `InputValidationError`. Loading/checksum failures raise `ModelLoadingError`; model failures raise `PredictionError`. Normal errors do not expose internal stack traces.

Unknown `primary_use` is accepted with an explicit warning and becomes all-zero one-hot indicators. Unseen building/site IDs are accepted with warnings because they do not enter the predictor matrix. Meter codes outside 0–3 are rejected. Raw negative predictions are clipped to zero and reported in response warnings.

## Inference API

The module provides `load_production_model`, `validate_prediction_input`, `build_feature_frame`, `predict_one`, `predict_batch`, `get_model_metadata`, and checksum verification. The model is cached process-wide; prediction is guarded by a read-only lock for practical thread safety. Responses contain the prediction, model version, UTC prediction timestamp, input timestamp, warnings, and a meter-dependent units statement.

- Source/package parity: passed at absolute tolerance `1e-10`

- Warm one-record median: 41.1 ms

These measurements support ordinary cached API inference on this machine but are not a latency SLA. Week 3 should cache one loaded model per worker and prefer batching where applicable. If deployment constraints are tighter, evaluate—but do not silently substitute—the smaller XGBoost challenger.

## Example

The package example supplies a 7,432 ft² education building, electricity meter code 0, building/weather attributes, and a 2016 timestamp. The actual packaged response predicts `174.33691959802735` meter-dependent units with no warning.

## Backend integration guidance

Week 3 should call `predict_one` or `predict_batch` from a service layer, translate `InputValidationError` into a client-safe validation response, cache the loaded package, record model version/warnings, and avoid rebuilding engineered features in routes or schemas. No endpoint, backend schema, Docker image, or deployment was created in this task.

## Remaining risks and readiness

Extreme readings dominate RMSE, test-period drift is substantial, R² is low, meter units vary, unknown categories lack a learned effect, and only one year was evaluated. The model is unsuitable for billing, safety control, or guaranteed savings. Subject to these limitations, the checksum-verified package and inference contract are **ready for Week 3 integration**. Week 2 is **100% complete**.
